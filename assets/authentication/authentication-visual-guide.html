01HTTP authentication scheme
Video 2:53 ↗

Basic authentication

Send a username and password with each protected request.

Think of it as Like showing your username and password at the door every time.

How it works

  • The server can challenge a request with 401 and a WWW-Authenticate header.
  • The client Base64-encodes username:password and sends it in the Authorization header.
  • The server checks the credentials. The client can send the same header on later requests without waiting for another challenge.

＋ Pros

  • Very small implementation; widely supported by HTTP tools.
  • No session database is required by the scheme.

− Cons

  • Reusable password travels on every authenticated request.
  • No built-in token expiry, fine-grained scopes, or reliable browser logout.

Base64 does not hide a password. Use HTTPS and protect credentials from logs.

Authorization: Basic YXJqdW46ZGVtby1vbmx5

Illustrative only: this decodes to arjun:demo-only.

Typical fit: Simple integrations or legacy HTTP endpoints where Basic is required.

02HTTP challenge–response scheme
Video 4:26 ↗

Digest authentication

Prove you know the password by answering a challenge.

Think of it as The guard gives you a fresh puzzle that depends on your secret.

How it works

  • The server sends a challenge containing a nonce: a fresh value used in the proof.
  • The client hashes password-related data together with the nonce and request details; the password itself is not sent.
  • The server computes the expected result and checks freshness. Matching proof establishes the identity.

＋ Pros

  • Avoids directly transmitting the password.
  • Nonce and counter checks can limit replay of captured requests.

− Cons

  • More complicated, with limited modern login features.
  • Captured exchanges can enable password guessing; old MD5 deployments are weak.

Digest is not limited to MD5: RFC 7616 also specifies SHA-256 and SHA-512/256. It does not encrypt traffic.

Authorization: Digest username="arjun", nonce="…", response="…"

Simplified header; real exchanges contain additional fields.

Typical fit: Existing devices and legacy systems that already require HTTP Digest.

Read more: HTTP Digest · RFC 7616 ↗
03Application / project credential
Video 6:12 ↗

API keys

A service presents a key issued to an application, project, or account.

Think of it as A membership key tells the service which account is calling.

How it works

  • An operator creates a key and configures any supported restrictions.
  • Your backend sends the key on API requests, usually in a header.
  • The API maps it to an account or project, checks restrictions, and applies its access and usage rules.

＋ Pros

  • Easy for scripts and service integrations.
  • Supports per-project quotas, billing, and key revocation where provided.

− Cons

  • A leaked secret key can be reused until restricted, revoked, or expired.
  • A key often identifies a project, not the person using it; capabilities vary.

Keep secret API keys on the backend. Some browser APIs use intentionally public, restricted keys; those do not prove user identity.

X-API-Key: <key-issued-by-provider>

Example header, not a universal standard.

Typical fit: Backend integrations, scripts, usage tracking, and APIs designed around keys.

04Server-side login state
Video 8:16 ↗

Session-based authentication

The browser keeps a session ID; the server remembers who it belongs to.

Think of it as A cloakroom ticket points to a record held behind the counter.

How it works

  • After a successful login, the server creates an unpredictable session ID and stores the user mapping.
  • The browser receives the ID in a cookie and sends it automatically on matching requests.
  • The server looks up the session, then checks permission for the requested action.

＋ Pros

  • Easy to revoke a session and implement logout.
  • Identity and session state stay under server control.

− Cons

  • Multiple servers need a suitable shared session strategy.
  • Cookies sent automatically create CSRF risk; stolen session IDs allow impersonation.

Use Secure and HttpOnly cookies, suitable SameSite settings, CSRF defenses, expiry, and session-ID rotation after login. HttpOnly does not make XSS harmless.

Set-Cookie: __Host-session=<random-id>; Path=/; Secure; HttpOnly; SameSite=Lax

Cookie = storage/transport mechanism. It can carry a session ID or another kind of token.

Typical fit: Browser applications that benefit from straightforward logout and central session control.

05Token presentation scheme
Video 10:00 ↗

Bearer tokens

Possession of a valid token is enough to use its granted access.

Think of it as A bearer ticket can be used by whoever is holding it.

How it works

  • A login or authorization flow issues an access token.
  • The client presents it in Authorization: Bearer ….
  • The API validates it through a lookup/introspection or, for suitable signed tokens, local verification; it then checks permissions.

＋ Pros

  • The API call does not contain the user’s password.
  • Works with both opaque strings and structured tokens such as JWTs.

− Cons

  • Anyone who steals a usable bearer token can replay it.
  • “Bearer” alone says nothing about format, expiry, revocation, or how it was issued.

Bearer describes how a token is used. JWT describes one possible format. Keep tokens out of URLs and logs.

Authorization: Bearer <access-token>

The token may be opaque or a JWT; the header does not tell you which.

Typical fit: APIs consumed by mobile apps, backends, and other authorized clients.

06Token format
Video 10:00 ↗

JSON Web Tokens (JWTs)

A compact container of claims that a receiver can verify.

Think of it as A signed pass carries details that a trusted reader can check.

How it works

  • An issuer creates claims such as subject, intended audience, and expiry, then signs the token.
  • The client passes it to the intended receiver. An API may receive a JWT as a bearer access token.
  • The receiver validates the signature, permitted algorithm, issuer, audience, and time claims before using the contents. It still checks permissions.

＋ Pros

  • Signature verification can avoid a session lookup for each request.
  • A standard format lets multiple services verify trusted claims.

− Cons

  • A signed payload is usually readable; secrets do not belong inside it.
  • Immediate revocation and changing permissions need extra design; claims may become stale.

Decoding is not validation. JWT does not automatically mean encrypted, stateless, or an access token.

<base64url-header>.<base64url-payload>.<signature>

The common signed JWS form is shown. Encrypted JWTs use a different structure.

Typical fit: Systems that need signed identity or access claims, often across several services.

07Token lifecycle pattern
Video 12:54 ↗

Access & refresh tokens

Use one token for API calls and another to renew access.

Think of it as A short-term entry pass plus a more protected renewal voucher.

How it works

  • A short-lived access token is sent to the resource API.
  • When it expires, the client uses a refresh token at the authorization server’s token endpoint.
  • The server validates the request and can rotate the refresh token, invalidating its predecessor. Revoked or expired refresh tokens require another login.

＋ Pros

  • Short access-token lifetimes limit the reuse window.
  • Users can continue working without repeatedly entering credentials.

− Cons

  • A stolen refresh token can provide longer access.
  • Rotation, safe storage, replay detection, and concurrent refreshes add complexity.

Access token → API. Refresh token → authorization server. For public clients, OAuth security guidance requires rotation or binding the refresh token to a client-held key.

POST /token
grant_type=refresh_token&refresh_token=<refresh-token>

Schematic request body. Confidential clients also authenticate to the token endpoint.

Typical fit: Token-based applications that keep people signed in while limiting access-token lifetime.

Read more: OAuth 2.0 · RFC 6749 ↗ · OAuth security · RFC 9700 ↗ · Token revocation · RFC 7009 ↗
08Authorization framework
Video 14:38 ↗

OAuth 2.0

Let an app access specific resources without giving it your provider password.

Think of it as Give a valet a limited key instead of your full keyring.

How it works

  • The app asks for a specific scope, such as reading a calendar. The provider handles login and approval.
  • A short-lived code returns to the app. The app exchanges it using the matching PKCE verifier.
  • The resulting access token authorizes API calls. The API enforces its scope and other permissions.

＋ Pros

  • Delegation without sharing the provider password.
  • Scopes can limit what the app may access.

− Cons

  • Redirects, consent, code exchange, and token handling require careful integration.
  • OAuth alone does not standardize a user-login identity result for your app.

Use a maintained OAuth library and Authorization Code + PKCE for this interactive flow. Other grants exist, including client credentials for services.

response_type=code&scope=calendar.read&code_challenge=<challenge>&code_challenge_method=S256

Partial authorization request. PKCE binds the returned code to the client that began the flow.

Typical fit: Connecting an app to a user’s calendar, files, or other provider APIs.

09Authentication protocol on OAuth 2.0
Video 16:14 ↗

OpenID Connect (OIDC)

A trusted provider tells your app which user has signed in.

Think of it as A trusted authority supplies a signed identity statement for your app.

How it works

  • Requesting the openid scope starts an OIDC sign-in flow.
  • The provider authenticates the user and returns an ID token through the code exchange.
  • Your app validates that token and the login transaction, identifies the account using the provider/subject pair, and can create a local session.

＋ Pros

  • Standard identity claims and interoperability.
  • The identity provider can handle MFA and credential management.

− Cons

  • Your login depends on the provider’s availability and security.
  • Token validation, account linking, and redirects must be configured correctly.

An ID token tells the client about authentication. Do not substitute it for an API access token. OAuth buttons do not all necessarily implement OIDC.

scope=openid profile

“openid” is the defining scope. Additional scopes request additional permitted information.

Typical fit: “Sign in with Google” and enterprise sign-in for modern applications.

10Sign-in experience / pattern
Video 17:41 ↗

Single sign-on (SSO)

Sign in at a shared identity provider, then move between connected apps.

Think of it as One identity check lets you enter several offices, each with its own access rules.

How it works

  • App A delegates login to the shared identity provider. The user signs in there.
  • App B later sends the browser to the same provider, which can reuse its existing login session.
  • The provider issues an app-specific result. Each app establishes its own session and enforces its own permissions.

＋ Pros

  • Fewer repeated logins and fewer app-specific passwords.
  • Central identity and MFA policies can serve many applications.

− Cons

  • Provider compromise or outages can affect several apps.
  • Logout, account provisioning, and ending existing app sessions need coordination.

SSO commonly uses OIDC or SAML. It does not mean every app shares one cookie or token; policy can still require reauthentication.

One provider session → separate, app-specific sign-in results

SSO is the outcome people experience, rather than a single wire protocol.

Typical fit: Organizations with several internal tools or connected SaaS applications.

11Federated identity protocol
Video 19:05 ↗

SAML 2.0

An identity provider sends an XML assertion that an application can trust.

Think of it as A trusted office sends a signed identity letter to the service you want to enter.

How it works

  • The application (SP) sends a login request to the identity provider (IdP) through the browser.
  • After login, the IdP returns a SAML response containing an assertion; the browser submits it to the app.
  • The app checks the trusted signature, intended audience/recipient, expiry, request correlation, and replay protection, then creates a session.

＋ Pros

  • Widely integrated in enterprise identity systems.
  • Apps can delegate authentication and receive agreed identity attributes.

− Cons

  • XML signatures, certificates, metadata, and clock handling add complexity.
  • Less natural for mobile/API flows; misconfigured validation is dangerous.

SAML is still widely used. Use a maintained library; a signed document must also be checked for the right recipient, timing, and request.

<saml:Assertion> … identity and conditions … </saml:Assertion>

Schematic XML. A SAML assertion is not a JWT or a general-purpose API access token.

Typical fit: Enterprise SaaS and organizations whose identity integrations use SAML.

One practical combination

How the pieces fit together.

Imagine an internal portal with several tools. OIDC can handle sign-in, a session cookie can keep the browser signed in, and an access token can authorize backend API calls.

For the person: sign in at the shared identity provider and move between connected tools. That experience is SSO.

For the application: verify the identity result, maintain its own session, and check permission for each protected action. It can keep API tokens on its backend.

This is one possible design; a mobile app or service integration may use a different combination.

No jargon left behind

A small glossary.

Client
The software requesting access: a browser app, mobile app, script, or backend.
Identity provider (IdP)
A trusted system that authenticates people and supplies identity information to applications.
Claim
A statement in a token, such as who it refers to, who issued it, or when it expires.
Scope
A named limit on granted access, such as permission to read a calendar.
Nonce
A value that helps tie a message to a particular challenge or login attempt and detect reuse.
PKCE
Proof Key for Code Exchange: the client starts with a challenge and later proves it has the matching verifier.
Opaque token
A token whose contents the receiving application cannot usefully read; a trusted lookup can supply its meaning.
CSRF
A malicious site tricks a browser into sending an unwanted request with automatically attached credentials, often cookies.
State
A random value used to link an authorization response to the login transaction that your app started.
Issuer & audience
The issuer is the trusted party that created a token. The audience is the application or API it is intended for.
Signature
A cryptographic integrity check. It helps a receiver detect tampering and verify the trusted signing party.
Federation
An application relies on another trusted system’s identity result instead of performing all authentication itself.
